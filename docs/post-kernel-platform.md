## Reuse, adapt, design
- Headless: upstream docs/free-kc.md identifies PureDarwin fork b3b4b2812fdd1c5c251dc3089b5a1a9e00d29970 for arm64 dyld/libSystem/launchd/zsh/toybox. Use as provenance reference, not a copied runtime. Version-matched x86 sources, generated headers, dependency and license closure, signing/trust semantics and real hosted PID1/application tests are required separately for Monterey and Tahoe. No permissive security stub adopted.
- Disk: XnuDisk and IOStorageFamily/HFS source path are a promising starting point. Revalidate IOKit class interfaces, page sizes, block I/O, ownership, flush/teardown and filesystem integrity. Open HFS path first, not APFS redistribution.
- Ethernet and input: existing BSD-2-Clause-Patent XnuEthernet and XnuInput classes plus host-side tools provide reference. Revalidate version ABI, HID report behavior, event lifetime, networking and permissions. Host backend remains Linux-owned.
- Display: XnuDisplay derives from IOMobileFramebufferLegacy with private arm-specific assumptions. Do not transplant those offsets or ABI. Need x86 and version-appropriate display adapter; first owned framebuffer, host viewer, resize, presentation, input. Keep protocol and generic pixel utilities where validated.
- GPU software: existing XnuCpuMetal, ObjC++ plugin, Rust bridge, metal2vulkan, Vulkan loader, lavapipe are candidates. Scripts are arm64/arm64e and Mac SDK-oriented; x86 build, pointer width/layout, alignment, page size, target SDK, framework/device discovery, synchronization and teardown need tests. CPU rendering before acceleration; no claim that Metal framework is open.
- GPU hardware: retained xnudrmd and optional xnudrmd_virgl backend, MIT protocol/Darwin bridge, Venus and test references. README and production docs disagree about physical GPU status. Production describes DGX Spark success but independent reproduction absent. Verify host-only backend on each actual supported GPU, then validate transport and lifecycle, then Darwin Vulkan, then Metal/graphics. Linux DRM/Vulkan drivers remain host-owned. Intel ANV, AMD RADV and NVIDIA NVK or other separately reviewed driver are candidates, not supported hardware claims. See https://mesa3d.org/ and https://docs.mesa3d.org/drivers/nvk.html.
- Kernel collection and build: kclink/kextld currently targets ARM64/e; x86 Mach-O relocation, target build, framework and generated-header closure require separate work. No ARM64 object or Apple kext import. Existing x86 recipes and test evidence stay primary.
- Desktop: upstream's full desktop relies on separately obtained proprietary macOS disk/frameworks and version-matched components; screenshots and reported ARM runtime are not x86 evidence. An open desktop requires a compositor, toolkit/framework subset and session services, not just Metal. Independently assess Darling, GNUstep and other open implementations as candidates; no external source imported. Darling's userspace server is not an automatic substitute for XNU; evaluate only separable framework/backend components with provenance and licenses.
- Seamless: upstream framebuffer snapshots, input helper and probe-window are not a complete per-window host integration. Need an original or licensed window/surface lifecycle and Wayland/X11 presentation bridge, focus/input/resize, clipboard, drag/drop, multiple displays, accessibility, clipboard permissions, audio and host resource arbitration. Use a common host protocol where compatible; separate Darwin version adapters where proven needed.
- Additional gaps: audio (CoreAudio-compatible bridge to PipeWire/ALSA), shared files and removable devices, camera/mic permissions, power management, user service lifecycle/recovery, packaging, diagnostics and application compatibility matrix. No complete implementations established by the inspected trees. Existing Linux subsystems preferred over new hardware drivers.

## Licenses
The root LICENSE is a map, not a single license. GPL-2.0-only host FKI/Linux, scripts and Linux GPU daemon; APSL-2.0 XNU, adapter and most kexts; BSD-2-Clause-Patent display/input/network and Metal shim; MIT DRM protocol/Darwin shim and Mesa/virgl patches; GPL-2.0-or-later CPU Metal plugin and metal2vulkan patches. Source-prefix scan: GPU 49 selected program-source files (9 GPL-2.0-only, 32 GPL-2.0-or-later, 7 MIT, 1 BSD-2-Clause-Patent), kexts 33 (27 APSL-2.0, 5 BSD-2-Clause-Patent, 1 GPL-2.0-only). All selected files have markers, but file scope, upstream attribution, patent notices, combined/linking obligations and transitive licenses remain unreviewed. Root directory summary lists mixed DRM test licenses; follow actual file notices. Upstream fetch scripts declare metal2vulkan GPL-2.0-or-later/LGPL-3.0-or-later, Vulkan-Loader Apache-2.0, Mesa 26.3.1 MIT, LLVM 22.1.8 (verify Apache-2.0 WITH LLVM-exception), Mbed TLS 3.6.8 dual license selected Apache-2.0. The AdrenoMetal fetch note and shim's different license require per-file provenance verification. Do not assume compatible combined distribution from SPDX labels alone; legal review especially GPL-2.0-only versus Apache-2.0, Rust dependency closure, and APSL boundaries. Preserve originals. No proprietary Apple SDK, frameworks, system disk, firmware, kexts or binaries without rights. Apple macOS licenses restrict complete OS use to Apple-branded computers; see https://www.apple.com/legal/sla/. Open-source kernel and open runtime are independent of permission for proprietary software.

## Proposed order (no change to existing gates)
1. Preserve Monterey hosted/AMD milestones and source closure. Prepare Tahoe read-only dependency inventory independently.
2. Open Darwin runtime, disk/network/input, service start/stop. Version-matched headless smoke on each target.
3. Software display path and minimal graphical session using owned/open applications.
4. CPU Metal candidate build and functional tests with compatible legally available frameworks.
5. Isolated Linux-only backend regression, hardware-specific capability matrix, then hosted GPU integration and lifecycle.
6. Separate full desktop and seamless presentation, audio, accessibility, files, app testing, packaging and release gates.
Do not build three independent kernels or duplicate the GPU transport by CPU vendor. No new physical modules without approval. ARM64 reference remains unchanged.
